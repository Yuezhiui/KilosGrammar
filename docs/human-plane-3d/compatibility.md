# Human Plane → 3D: gameplay compatibility contract

Read-only audit of the existing Godot 4.7.2 implementation on 2026-10-26. The planned visual conversion replaces the 2D airplane and rectangular answer arches with an actual 3D player/aircraft, environment, and torus-shaped answer rings with legible grammar text. This document specifies observable game behavior, scene integration, and regression coverage to carry forward. It does not prescribe the new 3D visual design.

`main_menu.gd:704-724` saves scores to local PostgreSQL **only** for a `results` event emitted while on the `gameplay` route with `round_completed == true` and a `score`. Human Plane itself neither writes to the database nor determines whether a save succeeds; it currently returns `score_saved=false` and `database_connected=false` in its game context (`human_plane.gd:205-210`). The router owns success/failure and populates the final Results screen. Do not connect new 3D collision signals directly to saving.

A process-disabled minigame must not continue rendering-dependent timers, simulation, collision or animation. The wrapper also suspends the minigame on prolonged camera loss.

## Session data and mode semantics

`human_plane.gd:189-211` returns a deep copy of input context plus the keys below. Consumers include the wrapper, Pause, Results, and completed-score persistence.

| Key | Meaning |
| --- | --- |
| `activity` | Exactly `Human Plane`. |
| `topic`, `game_style` | Both are the canonical grammar topic: `Noun`, `Pronoun`, `Verb`, `Adjective`, or `Adverb`. An invalid topic resolves to `Noun`. |
| `difficulty` | `Easy`, `Normal`, `Hard`; `Medium` aliases `Normal`, other unknown values default `Normal` at game level. |
| `game_mode` | `Seconds` or `Lives`; legacy `Quiz` falls back to `Seconds`, as does any value not in `lives/life/hearts`. |
| `score`, `correct`, `attempts`, `total`, `waves_completed`, `lives`, `streak` | Integer scoreboard/progress values. `total` is `waves_total`. |
| `time_remaining` | Nonnegative seconds left in `Seconds`; exactly `0` sentinel for untimed `Lives`. |
| `body_x` | Current aircraft position normalized to `[-1,+1]` (internally `plane_x_norm` in `[0,1]`). |
| `round_completed` | `true` only when the round finishes and results should be saved; explicitly `false` for Pause. |
| `demo_mode`, `gameplay_implemented`, `camera_live`, `score_saved`, `database_connected` | Currently `true`, `true`, `false`, `false`, `false` respectively in the raw game payload. The wrapper/router supplements the live camera/database state. |

`set_context` before startup restores positive/nonnegative counters, `body_x`, and `time_remaining`, clamps lives to three, and uses `context.total` with a minimum of ten waves. It does not serialize the actual current/next gate words or gate progress. Normal Pause/Resume does **not** reconstruct the instance; it retains it. A reconstructed scene is only guaranteed to restore the exposed counters/time/body X, so do not assume a mid-gate restart is supported (`human_plane.gd:265-296`).

| Difficulty | Total waves | Gate progress per second | Configured inter-wave delay |
| --- | ---: | ---: | ---: |
| Easy | 12 | 0.20 | 0.62 |
| Normal | 14 | 0.27 | 0.46 |
| Hard | 16 | 0.34 | 0.34 |

The config contains `inter_wave_delay`, but **current continuous-wave runtime does not wait between successive gates**. It sets `inter_wave_delay = 0` when promoting a prefetched wave (`human_plane.gd:421-447`). Preserve visible seamless handoff and the exact progress rates; do not inadvertently reintroduce the configured delays. `Seconds` runs for **exactly 60.0 seconds**, all difficulties. `Lives` has **no timer**, not a hidden 60-second timeout. **Both modes start with three hearts**; wrong/missed gates remove hearts even in Seconds mode. A round ends upon timer expiration (Seconds only), no lives, configured wave count, or legitimate word-bank exhaustion (`human_plane.gd:22-24,47-52,265-296,299-320,389-400,463-469`).

## Question, scoring, gate targeting, and collision

- Each wave presents **exactly three** answer candidates indexed `0=LEFT`, `1=CENTER`, `2=RIGHT`. `round_data` comes from `GrammarBank.lane_round(topic, difficulty, rng, used_round_words)` and supplies `prompt`, `options` (3 strings), and `valid_indices` (**one or two** unique indexes, never zero/three). `GrammarBank.is_matching(word, topic)` is the canonical correctness predicate (`grammar_bank.gd:181-228`). Difficulty affects vocabulary tiers and the probability of two valid answers: Easy 0%, Normal 20%, Hard 50% (`grammar_bank.gd:279-286`).
- No displayed word may repeat in the same session, **including wrong choices and upcoming preview options**, ignoring case/edge spaces. Every displayed word is immediately reserved in `used_round_words`; depleted vocabulary ends the round, never silently recycles options (`human_plane.gd:403-415,463-509`, `grammar_bank.gd:168-181`). Keep three choices and potentially two valid lanes even when showing words on the inside of 3D torus rings.
- The existing HUD asks `WHICH WORD IS A/AN <TOPIC>?` while **the gate labels show sample words** (e.g. APPLE, RUN, TEACHER), rather than all three rings literally reading NOUN/VERB/ADJECTIVE (`human_plane.gd:690-699,713-738`). The user's new torus-label request mentions grammatical categories; this is a gameplay-content decision: replacing sample words with category names would require corresponding changes to prompts/validation and should not accidentally mark every ring using old `valid_indices`.
- Resolve the selected ring **once, at the approaching answer plane**. Merely steering or touching a neighboring ring earlier never scores. In current 2D code, the gate center's **visible rendered texture** crosses editor `AnswerLine`; absent that guide, `GateEndCenter` is the fallback (`human_plane.gd:378-388,816-840`). At that instant `_lane_hit_at_answer_line` horizontally intersects the player's editor-authored `PlaneRig/Hitbox` with the *actual* visible gate art, excluding empty aspect-fit padding, and chooses first overlapping lane, else `-1` (`human_plane.gd:600-617,786-814`). The 3D answer plane and center/opening collision should be geometrically coincident with the rendered torus ring, ideally using actual ring inner opening + player bounds rather than an invisible oversized rectangle.
- Scoring occurs in `_resolve_at_answer_line()` with `gate_resolved=true` before applying effects, so re-entry cannot score twice (`human_plane.gd:567-598`). **Correct**: `+100`, `correct_count += 1`, `streak += 1`, no life restoration. **Wrong ring**: `-40` (floor zero), `streak=0`, one heart lost. **Miss all rings**: `-20` (floor zero), `streak=0`, one heart lost. All outcomes increment `attempts` exactly once. `selected_lane` is the hit index or `-1`, and `selected_was_correct` records success; HUD score/heart state updates immediately. Score does **not** depend on difficulty or streak multiplier (`tools/test_human_plane_fixed_score_speed.gd`).
- The gate progression value starts at `0`, increases linearly with the difficulty speed, and renders along a smoothstep interpolation between editor-authored start/end transforms (`human_plane.gd:750-769`). The active gates are legible through the scoring boundary and then fade out. At `gate_progress >= 0.32`, the upcoming set is prefetched, receives its *own* `next_round_data`, and approaches at `0.28 ×` speed. It starts at `max(0, gate_progress - 0.72)`; after active progress reaches `1`, the already-visible next set becomes active **at its current progress** with no respawn/pop or blank inter-wave delay. The passing set fades for `0.26 s`; post-answer active dissolve spans `0.12` gate-progress units (`human_plane.gd:25-32,368-447,772-783`). Existing scene has two authored sets under `MovingGates` and `UpcomingGates`; they alternate ownership of the active/preloaded visuals. This cadence matters for depth/perception in 3D.
- `_update_gate_wave` advances in steps no larger than `1/30 s` (max 150 steps) so dropped render frames cannot skip a collision. It stops the catch-up loop once a wave finishes: a long frame must not auto-fail multiple unseen questions (`human_plane.gd:351-365`). Completion increments `waves_completed` at the end of gate travel; scoring can occur earlier when crossing the answer plane. Stop new waves when finished and emit Results once.

The user asked to change arches into torus-shaped rings, with center text for grammar words/categories. The 3D implementation should show a genuine donut opening that a player can visibly fly through. Keep the three independently selectable answer lanes, one scoring boundary per wave, and readable text physically centered within/over each ring. Place exact collision boundaries to agree with the rendered rings and avoid scoring simply by choosing a lateral lane before reaching them.

## Camera, pose, motion, and input restrictions

1. All three position samples are **actually calibrated** by the camera, in the order `CENTER → RIGHT → LEFT`. Calibration cannot continue without all three valid measurements, and center-only synthetic bounds are rejected for Human Plane (`calibration.gd:252-259,423-429,602-635`). `PoseService.normalized_body_x()` returns `-1/0/+1` at measured LEFT/CENTER/RIGHT, using independent linear ranges on either side of the measured center (`pose_service.gd:339-370`).
2. A player must have a **fresh, tracked pose with both arms extended sideways** to steer. `PoseService.has_airplane_pose()` requires `has_fresh_gesture_pose()` and `airplane_pose=true`, with gesture freshness **650 ms**, stricter than the regular pose validity bound of **1,750 ms** (`pose_service.gd:9,20,298-325`). Outstretched arms only enable movement; **standing/stepping left/right** sets its signed direction. Wing roll/tilt does not steer. `gameplay.gd:355-365` updates the active flag and `gameplay.gd:315-342` forwards smoothed measured X.
3. `set_body_x(x)` accepts signed `[-1,+1]` (clamped) but only while pose-active, not paused/finished, and finite. It transforms into `[0,1]`, and `_update_plane_motion(delta)` approaches the target with exponential gain `10/s`, max travel `1.6` normalized-plane units/second and max integration step `0.10 s`. The wrapper applies another `12/s` smoothing on incoming YOLO samples (`human_plane.gd:33-37,214-220,322-333`, `gameplay.gd:321-332`). These limits prevent snapping at 30 and 60 FPS or after frame hitches.
4. On one arm lowering, lost tracking, or pose deactivation, freeze **the current X exactly**, clear old movement target, and wait for a *new* eligible body sample after reactivation. No autoconverging to center, remembered velocity, roll steering, synthetic keyboard/A/D or mouse steering (`human_plane.gd:229-237,322-333`, `gameplay.gd:282-284`). Visual bank/bob must not move the actual collision object; the old sprite only banks up to ~3° and bobs ~2 native px (`human_plane.gd:336-348`).
5. If all valid pose is lost, the wrapper stops gesture input immediately, then after **0.65 s** displays its Tracking Notice and sets the minigame's process mode to `DISABLED`. When tracking returns, it resumes the **same** game, with waves/time unchanged. It avoids showing the notice during guided tutorial/countdown (`gameplay.gd:289-313`). During the tutorial only, the wrapper directly calls motion but keeps gameplay processing disabled (`gameplay.gd:375-390`). The 3-second countdown must likewise freeze game state (`gameplay.gd:86-94,197-251`).
6. Human Plane connects `HUDLayer/HUD/PauseButton.pressed` to `_pause`. `ESC` or `P` also invokes `_pause` and handles the event (`human_plane.gd:170,642-650`); router ESC routes through gameplay `_pause()` (`main_menu.gd:1328-1339`). Do not allow an `ESC` from a guided screen to bypass the tutorial/countdown (`gameplay.gd:404-410`).

The script captures authored flight and artwork offsets rather than hardcoding absolute pixel locations (`human_plane.gd:138-169,739-762,843-850`). If replacing 2D travel guides with 3D Marker3D coordinates, keep position/scale/progression editing possible in the Godot editor; the gameplay math and collision must use the same marker transforms as rendering.
